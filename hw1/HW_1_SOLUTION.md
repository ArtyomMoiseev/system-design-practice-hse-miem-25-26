## Этап №1: Думаем и проектируем

Основные метрики, на которые будем обращать внимание:

1. RPS - Число запросов в секунду. Будем смотреть на число запросов к контроллерам GET /api/orders, POST api/orders. Число усепшных запросов (200), число неуспешных (500). Также будем образать внимание на latency (время выполнения запроса). Все эти метрики нам отдаёт k6, они у нас выведены на дашборд k6 Prometheus.
2. Будем смотреть на метрики связанные с нашей БД. Наиболее инетерсные из них для нас - rows (fetched, returned, inserted, updated), QPS - число запросов в секунду, число подключений.
3. Метрики связанные с железом - нагрузка на диск, CPU сеть и.т.д.

В целом для нас самое главное свести к минимуму число 500-x ответов, добиться среднего времени ответа в 500мс. При этом не перегружать БД и железо.

## Этап №2: Стреляем

1. Сценарий "Шторм" - резкий пик нагрузки (1000 пользователей за 10s)

```
export let options = {
  stages: [
    { duration: '10s', target: 1000 }, 
    { duration: '20s', target: 1000 },
    { duration: '20s', target: 0 },
  ],
};
```

2. Сценарий "Волна" - плавное нарастание (0 к 500 пользователей за 2 минуты)

```
export let options = {
  stages: [
    { duration: '2m', target: 500 },
    { duration: '1m', target: 500 },
    { duration: '30s', target: 0 },
  ],
};
```

3. Сценарий с длительной нагрузкой (за 2 минуты повышаем число пользователей до 300, а затем держать нагрузку в 300 пользователей в течение 10 минут)

```
export let options = {
  stages: [
    { duration: '30s', target: 50 },
    { duration: '90s', target: 300 },
```

## Этап №4: Анализируем

1. Самое главное и основное решение проблем - горизонтальное масштабирование, необходимо увеличить число инстансов приложения чтобы держать такую нагрузку. Позже - шардирование, чтобы могли держать более высокую нагрузку на запись.

2. Обязательно стоит настроить rate limiting в nginx, чтобы не перегружать бэк. Также стоит в архитектуру добавить pgbouncer - во время тестов до потолка не добрались (Для Postgres норм потолок около 300), но при увелечение нагрузки можем добраться.

3. Оптимизируем приложение, используем limit&offset для получения списка, чтобы не тянуть сразу все объекты
